# 試験運用・更新・復旧の手順

## 今回の公開範囲

- 利用者は公開サイトのURLだけで利用できます。ログイン・環境構築は不要です。
- GitHubは非公開のままです。告知文に「OSS」「ソース公開」「各自でそのまま構築できる」と記載しません。
- お問い合わせはコミュニティの告知スレッドへ誘導します。私的な情報をスレッドへ投稿しないよう案内します。
- 実際のスマートフォンで指操作を確認するまでは、「実機確認済み」と案内しません。

## Sitesで既存サイトを更新する

Sitesプラグインを使えるCodexで、対象リポジトリを開いて依頼します。たとえば：

> Sitesを使って「ご都合うかがい君（仮）」の変更を検証し、現在のサイトを更新してください。既存のproject_id・公開範囲・DBを維持し、GitHubは非公開のまま同期してください。管理・編集キーと回答データは送信しないでください。

1. `.openai/hosting.json` のIDに対応するサイトと、現在の公開範囲を確認します。
2. Sitesの標準手順で現在のソースを開き、差分を確認します。
3. 型チェック、単体テスト、ローカルDBでのAPI検証、表示確認を行います。
4. 変更したDB構造は新しいSQLとして追加します。適用済みSQLは編集しません。
5. `SERVICE_SIGNING_KEY` の設定があることを確認します。値をログに出さず、他の環境変数は維持します。
6. Sitesの標準手順でビルド・ソース送信・公開版保存・公開を行います。Sitesが未適用の本番SQLを適用します。
7. 公開結果とDBの表構成を確認し、同じソースの変更履歴をGitHubへ同期します。

今回のDB変更は `request_limits` 表と期限の索引の追加だけです。既存の `events` / `answers` の内容や構造は変更しません。
直前のSites版を再公開すれば、画面・処理を戻せます。追加した表は残してよく、切り戻しのために削除する必要はありません。署名鍵も維持します。

## 自分用の別サイトを作る場合

現在はソース配布を案内していません。将来、許可を得て複製する場合の注意点です。

- 元サイトの `.openai/hosting.json` の `project_id` を使って公開しないでください。
- Sitesで新しいプロジェクトを作り、返された新しいIDを複製側の設定に保存します。元のリポジトリや本番用IDは変更しません。
- Git履歴、認証情報、`.env*`、`.wrangler/`、ローカルDB、バックアップ、既存のサイト識別子をひな形へ混ぜません。
- 新しい署名鍵を新しいSitesの秘密環境変数へ設定します。新しいDBから開始します。
- 「今のサイトを更新」ではなく「元サイトを維持して新しいサイトを作る」と明示してCodexへ依頼してください。
- ChatGPTのプロジェクトへのZIPインポートだけでSitesが公開できる、という手順は検証していません。
- 自分のCloudflareへ直接公開する手順も未検証です。必要になった時に、この固定バージョンの構成に対応する設定を作成・検証します。

## 主催者の手動バックアップ

1. 管理URLで管理画面を開きます。
2. 「バックアップを保存」でJSONファイルをダウンロードします。
3. JSONファイルと管理URLを本人だけがアクセスできる場所へ保管します。GitHub・コミュニティ・共有フォルダへ送信しません。
4. 新しい回答が集まった時、回答を削除した後、重要な設定変更の後に保存し直します。
5. 削除した回答が入った古いファイルや不要になったファイルは、端末側でも処分します。

バックアップはイベント1件の設定・回答・作成/更新時刻・権限のハッシュです。署名用の秘密鍵、管理・編集キーの元の値、他のイベントは含みません。
署名用の秘密鍵はSitesが管理します。バックアップから取り出すことはできません。

## 誤削除したページを復旧する

1. 元の管理URLを開きます。ページが削除されていても復旧欄を表示します。
2. 「バックアップファイル」で元のJSONファイルを選びます。
3. 「バックアップから復旧する」を押します。
4. 回答数、〇・△、コメント、設定を確認します。
5. 元の集計・回答URLが使えることを確認します。元の編集URLも維持されます。

管理URLと署名されたバックアップの両方が必要です。存在するページは上書きしません。改変、別のイベント、別の管理権限、100回答を超える内容は拒否します。
復旧は全件まとめて反映し、一部だけ戻る状態を避けます。保存後の回答・編集は復旧できません。

### 復旧の範囲と限界

- 手動で保存していない内容は戻せません。ファイルや管理URLがない場合は、新しい調整ページで回答を集め直します。
- 元のSitesと署名用設定を維持することが必要です。別サイトへの持ち込みは想定していません。
- DB全体の障害・Sitesプロジェクト自体の削除・署名鍵の消失・基盤の障害からの復旧は未検証です。運営側の全体バックアップとは区別します。
- 稼働中ページの巻き戻しや、回答1件だけを自動復旧する機能はありません。
- 古いバックアップは削除済み回答を再表示する可能性があります。削除の希望があった回答を復旧しないよう、最新ファイルを使います。

## 投稿制限が発生した場合

HTTP 429の `Retry-After` が再操作までの秒数です。回答内容は画面に残ります。
同じ接続元の上限を超えた要求は、サイト全体の作成枠を消費しません。編集キーを変えても同じ接続元の上限は変わりません。
同じネットワークを使う複数人が制限を共有する場合があります。問題が続く場合は告知スレッドへ、発生時刻・操作・エラーを報告してもらいます。
この対策はアプリの更新処理の保護です。読み取り通信や分散攻撃への包括的な保護を保証しません。実際の濫用が発生した場合は、Sitesで利用できる基盤側の対策を確認します。

## 検証

ローカルでは新しい `0001_request_limits.sql` だけを既存DBへ適用します。新規DBは `0000`、`0001` の順です。
READMEのダミー署名値を使い、`tests/security.test.mjs` と `tests/api.test.mjs` で投稿上限、同時要求、ファイル改変、権限、削除・復旧を検証できます。
本番でテスト回答を作る必要はありません。運用データを使った破壊的な復旧試験は行いません。
